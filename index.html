1.1 Vision

Nubra AI Mode is the Agentic Broker: a natural-language layer that covers everything Nubra's platform and data already support for a trader, so a trader never needs to leave the chat to research, decide, or act. Not an assistant bolted onto the app — a complete, trustworthy front door to everything Nubra already offers, exposed through conversation instead of navigation.

This is deliberately not a claim to invent capabilities beyond what Nubra's platform and data already provide. The scope is comprehensive coverage of Nubra's real, existing workflows and data — not a speculative expansion into unrelated territory.

1.2 Primary user

The trader — not a fixed persona split between "beginner" and "expert." AI Mode adapts tone and depth to signals already present in the conversation (vocabulary, specificity, the complexity of the trader's own portfolio) rather than committing to one static personality. A first-time options trader and someone running a multi-leg book get the same underlying correctness guarantees; what adapts is how much is explained, never what is true.

1.3 Success definition

Primary metric — Workspace completion rate: the % of a trader's Nubra-related actions (research, screening, strategy construction, order execution, portfolio/risk review, reporting) completed entirely within AI Mode, without falling back to the manual UI.

GuardrailTarget
Factual / numeric error rateTrending to zero — see hard constraints
Unintended-order rateZero, always, by construction — not by monitoring alone
Session return rateA trader who used AI Mode once comes back and uses it again

A high completion rate achieved by cutting corners on the guardrails is not success — the guardrails are the constraint the primary metric operates inside.

1.5 Non-negotiable hard constraints P0

Not aspirations to balance against other priorities — the floor. Every item is informed by a real, confirmed failure found in this codebase, expandable below.

  • 01Never state a number — including in a teaching example — that isn't traceable to a real, verified source.
    Evidence
    A Greeks lesson used NIFTY lot size = 75 in its worked examples, contradicting the same conversation's own correct answer of 65 minutes earlier. Use real current data or an algebraic placeholder — never a fabricated concrete figure.
  • 02Never contradict itself on identical underlying data, within one conversation or across two.
    Evidence
    The same RELIANCE PCR numbers were labeled "bullish" in one conversation and "bearish" in another; the same option was quoted at two different prices one turn apart with no market movement.
  • 03Never silently fail to use the right tool and fabricate or hand-wave an answer instead. State the gap plainly, with the closest real alternative offered.
    Evidence
    Three different real report requests in one conversation all got a generic "I wasn't able to complete that, try rephrasing" with zero explanation.
  • 04Never let an unverifiable, self-computed number reach the user unflagged.
    Evidence
    ×100 and ÷10 arithmetic slips recurred across this testing effort whenever the model computed a total itself instead of relaying a tool's own authoritative figure.
  • 05Never place, modify, or cancel an order without the authorization the active execution mode requires. Any authorization mechanism must be provably firing in production, continuously monitored — see §1.7.
    Evidence
    A confirmation gate silently never fired for months — 78 turns, 55 traces, seven real orders placed with zero approval events — before an audit caught it. See §2.8.
  • 06Never expose credentials, session tokens, or another user's account data. Already correctly enforced — confirmed via live testing that a request for a different account's positions is refused.
  • 07Never claim a capability the product doesn't actually have. State the gap; never role-play around it.
  • 08Never leak internal reasoning, retry artifacts, or implementation details into user-facing text.
    Evidence
    A response once opened with "This is a learning question — let me route you to the mentor. Let me teach you directly." — two contradictory stated intentions in one reply.
  • 09Never issue a direct Buy/Sell directive. Analysis, screening, and mentor responses present real numbers and let the trader draw their own conclusion — "based on these numbers, this looks like the stronger side," never "you should buy/sell X." Applies everywhere AI Mode surfaces market analysis, not just Mentor.

1.6 Interaction principles

Ambiguity & scope

  • Stakes decide whether AI Mode clarifies first. Anything that commits money, is hard to undo, or could be misread gets a clarifying question first. Most zero-stakes, fully-reversible information requests get a sensible default immediately instead.
  • Screener requests are the deliberate exception. A bare "give me some trade ideas" is genuinely underspecified, so AI Mode asks a few lightweight scoping questions first — exchange, options vs. equity, intraday vs. positional. None are required: one answer, or none, is enough to run the screen with sensible defaults and show real results, framed as things to explore, not a final answer.
  • Clarification must converge. Never repeat an unanswered question turn after turn; accept a partial answer and proceed on the rest reasonably.
  • Long, multi-domain chains execute autonomously, however many specialists they cross. If a step genuinely fails (a real tool error, not a capability gap), the chain stops and reports exactly what succeeded and what broke — never fabricates the rest, never discards completed partial results.

Correctness & conflict resolution

  • Deterministic by default. The same well-specified request against the same data should produce the same structural answer.
    Evidence
    An identical "bear call spread, short 23400, long 23600" request resolved to the exact requested strikes in one conversation and to unrelated, scrambled strikes in another, minutes apart.
  • Every number carries a visible verification marker, either way. A verified figure gets a positive, designed indicator; an unverifiable one gets a distinct marker of its own — evolving today's inline "⚠ not verified" text into a real UI element.
  • Capability gaps are always named, paired with the closest real alternative. Never a dead end, never a disguised limitation.
  • Cross-agent conflicts resolve by freshness, silently. When two agents' views of the same fact disagree — a cached figure vs. a live re-check — the freshest direct broker-API call wins over any cached or derived figure, applied silently rather than surfaced as noise.

Domain-specific behavior

  • Strategy recommendations always resolve through the existing strategy module — iron condor, straddle, strangle, and the rest of the regular catalog on Nubra's own Strategies page — filtered by real available margin. Never an invented structure, never something the trader can't afford.
  • Reports mirror whatever the real Nubra APIs support, in whatever form those APIs actually support — a quick summary stays inline, a formal statement generates a real document. Full coverage, no silent gaps.
  • Alerts execute exactly as specified, no quality judgment. AI Mode owns creating/curating alert definitions but rides Nubra's existing notification system for delivery; it will create a price alert at the current price even though that fires instantly — the trader is in control.
  • Watchlist/alert suggestions are proactive, creation never is. AI Mode may suggest one when the conversation clearly signals it'd help, but always waits for an explicit yes before creating it.
  • Portfolio & Risk stays strictly reactive. It answers what's asked and does not surface an unprompted risk warning while answering something unrelated, even if it notices something material — trading a little proactive value for avoiding alert fatigue.
  • Mentor stays neutral within compliance bounds. It explains mechanics accurately, including for a clearly high-risk question, without editorializing on the trader's own choice — that judgment belongs to the trader.
  • Market Circulars is a normal, trader-facing domain — a trader can ask "what's the margin rule for this expiry" directly, same as any other domain.
  • Account scope needs no resolution logic. AI Mode is credential-driven; one credential maps to exactly one Nubra account.

1.7 Execution & authorization model

The most consequential part of the vision — the one place a wrong answer becomes a real, hard-to-reverse financial action. Grounded in the product's own current design (compare against §2.8), not invented from scratch.

  • The trader controls a global mode: Ask-for-Approval or Auto. Absolute — never silently overridden by order size, risk, or any other heuristic.
  • Auto mode: the order payload is created and shown with a 3-second cancellable window. Silence fires it; an explicit cancel inside the window doesn't. This is what makes "a fully-specified instruction IS the authorization" safe rather than irreversible-by-accident.
  • Ask-for-Approval mode: an explicit cross-question is shown and the system waits indefinitely for a yes/no — no timeout that silently discards or fires the order.
  • Risk-reducing actions (cancel, square-off) get different treatment than risk-increasing ones. Reducing risk doesn't need the same friction as adding it.
  • An agent-derived structure carries the same trust as an explicit typed order, once the trader has seen it and said to place it. "Build me a bear call spread" → "place it" is not lower-trust just because the agent resolved the strikes.
  • A conditional/trigger order's original setup is sufficient authorization for whenever it fires. No second confirmation days later when the condition is met.
  • Any authorization mechanism must be provably firing in production, continuously, automatically. "We built a gate" is not sufficient — zero observed events across real traffic must trigger investigation automatically, not an audit six months later. See the N-01 incident in §2.8.

2.1 What this actually is, from basics

Everything in Part 2 describes what exists today, verified against the live codebase as of 2026-09-21 — not a restatement of Part 1's aspirations.

Nubra AI Mode is a chat interface in front of Nubra's real trading platform. A trader types a message; it's answered or acted on using Nubra's own live account data and broker APIs — the same data and APIs the regular Nubra app uses, never a simulated environment.

Three pieces do the work:

1. Backend API — orchestrator/backend-api, a Node/Express server. Receives the chat message, manages the conversation, streams the response back.
↓
2. AI orchestration layer (OpenCode) — the Orchestrator agent reads the message, figures out which specialist(s) it's about, hands it off. Each specialist knows one kind of job and nothing else.
↓
3. MCP tool servers — reference/nubra-mcp-deploy, the code that calls Nubra's real broker APIs (api.nubra.io) for quotes, positions, option chains, or to place an order. The only layer that ever touches Nubra's real backend.

So one message flows: trader → backend API → Orchestrator → specialist agent(s) → MCP tools → Nubra's real broker APIs → back up the same chain → trader.

2.4 What more agents would we need?

Assessment: the 13-agent taxonomy is structurally sound for the north star. Almost every domain in §1.4 already has a home in an existing specialist. The real gap is tool-coverage completeness and correctness infrastructure within existing agents, not missing agent categories:

  • Backtesting is pulled entirely out of chat — conflicts with "never need to leave AI Mode." Not a new-agent case — reinstate backtesting-strategy's in-chat path.
  • Reports coverage is partial — a tool-coverage gap inside the existing reports agent, not a missing agent.
  • The correctness/verification pipeline is intentionally not an agent — cross-cutting infrastructure every agent's output passes through.
  • Gate monitoring is platform observability, not a chat-facing agent.

No open item points to a genuinely new specialist category beyond these 13. One honest caveat: the reports-domain API research flagged as a follow-up could surface a document type that doesn't fit any current agent's domain — revisit once that's done.

2.5 The number/date correctness pipeline

Where most recent engineering effort has gone — directly tied to constraints #1–#4.

  • tools/_tagging.py — wraps every numeric/date leaf in every tool response as [[N:...]]/[[D:...]], structurally, by value shape, not field name. Makes the model's job "copy a tag verbatim," not "type a number from memory."
  • tools/_money.py — older, field-name-based MoneySpec conversion of declared money fields from broker wire-scale to rupees. Still in use; tagging is the newer, universal layer on top.
  • responseSafety.ts — three checks on the model's final text: verifyAndRenderTags (confirms every tag matches real tool output), markUnverifiedViolations (inline "⚠ not verified" fallback), flagStrategyScaleMismatches (catches a stated number at a clean 100×/1000×/0.1× multiple of the verified value).
Two bugs fixed 2026-09-18 & known remaining gaps

parseMoneyShaped never stripped the tag wrapper before parsing, and extractStrategyGroundTruth/collectExpiryDisplays required a parsed object when real output arrives as a raw JSON string — both silently made their checks no-ops in production. Fixed, and covered by tests using the real string-shaped data format.

Remaining: flagStrategyScaleMismatches compares magnitude only, not sign; it can also false-positive (once flagged a Vega value as "off by 0.1×" purely because it divided cleanly into an unrelated Max Profit figure — the check doesn't yet know which numbers are semantically comparable).

2.6 The dispatch/registry chokepoint

tools/dispatch.py and tools/registry.py — every one of the ~138 tools is published through one registration loop. A tool declares money=MoneySpec(...) on its ToolEntry, and the chokepoint converts centrally. This exists because the same money-scale bug (tracked as F-040) recurred twice before this pattern: a fix to one tool (strategy_analyze_legs) didn't carry over to a sibling tool (strategy_list_prebuilt) with the same money fields. No per-tool code to forget, no "wrong tool got the fix" failure mode.

2.7 Strategy tooling

tools/strategy_actions.py — strategy_analyze_legs was merged into strategy_list_prebuilt's custom_legs parameter (2026-09-18): a caller gives {option_type, side, offset_type, offset_points} per leg, and the server resolves the actual strike/ref_id/price from the live option chain — the model never resolves a leg by hand. custom_legs also supports a per-leg expiry, which is what makes calendar spreads work.

Resolved product decision, open implementation gap: "N lots" always means quantity = N lots — trust the trader's literal phrasing and multiply against the instrument's real lot size. The tool currently always resolves quantity: 1 regardless of what's asked, so every "ground truth" figure this tool produced this session answered a narrower question than several real prompts actually asked (e.g. "65 lots" was silently treated as 1 lot). Needs a real lots/quantity parameter resolved by the tool itself against the live lot size — not left for the model to multiply by hand, which is exactly the failure mode in constraint #4.

2.8 Execution safety — today vs. the ideal model

Worth stating plainly — the most consequential gap between what's documented and what's real.

The N-01 incident (from execution.md's own code comment, dated 2026-09-04): six committing tools were gated behind a permission-ask mechanism. Measured across a 78-turn, 55-trace release-gate run, that gate never fired once — no permission.asked observation exists anywhere in that data, and seven real orders were placed with zero approval events. The response was a policy change, not a gate fix: "a fully-specified prompt IS the authorisation — it is placed immediately... There is no separate approval step." That is the live, current behavior of the execution agent today.

How this compares to §1.7's model: the "fully-specified instruction is the authorization" principle is already real and shipped. The 3-second cancellable window described as current UI/backend behavior lives on the frontend/order-bridge side, which this session's work did not touch or inspect — it should be verified against the real frontend code before this document asserts it's fully built, rather than assumed from description alone.

The existing architecture PRD's Sections 11 and 16 describe a stricter, not-yet-shipped model ("the AI must never place an order silently in Ask for Approval mode"; "Full Auto: design proposal only, not implemented, pending compliance sign-off") that doesn't match what's actually running. Worth resolving explicitly with whoever owns compliance sign-off — not left implicit across two disagreeing documents.

Part 3 Phased path to the north star

  1. Foundation — built

    Multi-agent orchestration, the 13-agent taxonomy, per-user identity/multi-tenant isolation, core read/analysis domains, the IBT-compliant execution shape.

  2. Correctness infrastructure — in progress

    Universal tagging, the dispatch chokepoint, deterministic tool-call verification for strategy math, strategy-tool consolidation — plus closing the remaining gaps in §2.5 and §2.7 (scale-check sign/relevance precision, the lots-to-quantity implementation gap).

  3. Capability completeness

    Full reports-domain coverage against the real Nubra API surface, re-enabling backtesting in chat, and a systematic sweep of the remaining ~130 tools for the same class of undeclared-field bugs found in the strategy domain.

  4. Verification UX

    Replace the inline "⚠ not verified" text tag with the real designed verified/unverified marker from §1.6 — visible on every number, not just the exceptions.

  5. Full workspace

    Comprehensive, gap-free coverage of every domain in §1.4; the 3-second-window/cross-question execution model fully verified end-to-end and continuously monitored; resolution of the compliance divergence noted in §2.8.
